## Common model-facing routes

**Session-shell tools:** `OpenSessionShell` / `SessionShellExec` are typed `ToolCall` variants (`crates/webcodex-tool-contracts/src/tool_call.rs:2308-2345`); their operation names are mapped at `5692-5695`. The Runner-side handler is `PersistentShellManager::handle_operation` (`crates/webcodex-runner/src/webcodex_runner/persistent_shell.rs:52-131`), which boundary-validates before open/exec/status/close. Local open calls `ProcessManager::open` → `webcodex_persistent_shell::PersistentShellManager::open` → platform `spawn_shell_process` (`persistent_shell.rs:563-605`). SSH open calls `RemoteShellTransport::spawn` (`persistent_shell.rs:172-220`, `remote_shell.rs:79-145`).

**Detached-job tool:** the MCP Server passes `tools/call` into `ToolRuntime::call_tool_with_invocation_metadata` (`src/mcp.rs:1275-1292`; `src/mcp/tools.rs:2652-2686`). `ToolRuntime::dispatch` routes `RunDetachedProcess` through `dispatch_shell_tool` (`src/tool_runtime/dispatch.rs:2397-2403`; `shell_tools.rs:7-67`); `run_detached_process_with_contract` resolves the Runner project/cwd and calls the Runner Registry Job-start API (`process.rs:490-645`). The Registry constructs `RunnerJobOperation::StartDetachedProcess`, wraps it in `RunnerOperation::Job`, and serializes the request (`crates/webcodex-runner-registry/src/job_updates.rs:1045-1113`; typed variants in `crates/webcodex-core/src/runner_operation.rs:137-145,652-680`). Runner dispatch converts that invocation into `PendingJobStart` and calls `JobManager::enqueue` (`crates/webcodex-runner/src/webcodex_runner/dispatch.rs:745-765`); `enqueue` records/admission-checks and may place it on the local queue, then `start_now` selects `start_detached_process_job` (`job_manager.rs:2280-2434`). The worker prepares argv/env/cwd and hands off to the detached supervisor (`job_manager.rs:2483-2638`; `detached_job.rs:1905-2033,2258-2431`). This is the durable Job path; it is distinct from the Session-shell manager path below.

**Persistent Session-shell tools:** `tools/call` enters the same Server/ToolRuntime boundary (`src/mcp.rs:1275-1292`; `src/mcp/tools.rs:2652-2686`), and `OpenSessionShell` / `SessionShellExec` route to `dispatch_session_shell_tool` (`src/tool_runtime/dispatch.rs:2405-2410`; `session_shell.rs:339-365`). `open_session_shell` / `session_shell_exec` create a `PersistentShellRequest` and call `run_runner_persistent_shell` (`session_shell.rs:386-555,558-760`); that helper enqueues a request which Registry encodes as `RunnerOperation::PersistentShell` (`session_shell.rs:917-950`; `crates/webcodex-runner-registry/src/requests.rs:2192-2248`; variant at `crates/webcodex-core/src/runner_operation.rs:652-680`). Runner dispatch calls `PersistentShellManager::handle_operation` directly (`crates/webcodex-runner/src/webcodex_runner/dispatch.rs:568-592`), which validates boundary and selects local or SSH operations (`persistent_shell.rs:52-131`). Local open proceeds through `ProcessManager::open` to platform `spawn_shell_process` (`persistent_shell.rs:382-434,563-605`; `crates/webcodex-persistent-shell/src/lib.rs:1918-1969`; Windows: `crates/webcodex-persistent-shell/src/windows.rs:249-303`). SSH open calls `RemoteShellTransport::spawn` and the transport's platform-backed SSH child (`persistent_shell.rs:134-231`; `remote_shell.rs:79-145`). Persistent shell is not submitted to the detached Job queue.

## Cross-surface findings (facts only)

1. **Persistent Session shell and detached Job are different contracts.** Persistent shell is a Runner-local in-memory manager keyed by Session/shell identity; Runner restart loses its manager/transport. The detached path persists a Job record and transfers accepted ownership to an internal supervisor. Treating the former as an already durable job, or wrapping the latter in a normal process owner whose drop kills it, would change lifecycle semantics.
2. **FD7/8 belong to the persistent shell protocol.** Local Unix shell additionally reserves FD9 for control. Remote SSH reserves remote FD7/8 because its SSH exec channel has no extra control FD. Detached handoff uses stdin/stderr handshake and Unix watchdog stdin EOF; do not conflate these channel contracts.
3. **Detached process identity is stronger than PID.** Record carries PID, random creation id, native OS start id, timestamp; recovery also requires the process lifetime lock. macOS uses `proc_pidinfo`, Linux `/proc/<pid>/stat`, Windows process creation time (`detached_job.rs:1025-1204`). This is source evidence; it does not constitute a runtime PID-reuse test result.
4. **Current confinement is not established by P1B classification.** The detached preparation path checks local Runner policy/cwd, resolves executable, and snapshots environment, and payload clears inherited env. The accepted inventory still says `production confinement NOT_PROVEN`. No source-only claim here promotes that to a sandbox PASS. Persistent remote shell additionally carries remote host, credential, and network authority outside the local shell broker.
5. **OS asymmetry:** Unix has `setsid`, process-group ownership and watchdog; Windows has Job Objects and a narrow breakaway fallback for the detached supervisor. Inventory includes only the Unix watchdog row because there is no Windows watchdog implementation.
